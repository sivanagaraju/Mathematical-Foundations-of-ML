01 / Main recommendation

Keep execution outside the request lifecycle

For a pipeline that takes 10–60 minutes, use submit → run ID → poll status → final exit code. The submission API records the request durably and returns quickly. A separate worker performs the pipeline.

AutoSys still waits. The HTTP connection does not.The wrapper stays running and sleeps between status checks. It returns exit code 0 only for a durable SUCCEEDED result. Acceptance, a running pod, and an HTTP 200 status lookup are separate milestones.

Think of a parcel shipment: obtaining a tracking number means the shipment has been registered; the delivery status tells you when the work is complete. The run ID is your pipeline’s tracking number.

What you described

  • A request supplies a pipeline name.
  • The API retrieves source-to-destination metadata and performs a long process.
  • AutoSys invokes it through your OpenShift setup.
  • AutoSys needs the real completion result.

Assumptions for this proposal

  • You can modify the API and add shared durable storage.
  • Your execution code can run in a separate worker.
  • A Kubernetes Job is suitable if each run needs its own pod.
  • Pipeline names, endpoints, timings and deployment snippets here are illustrative.

AutoSys, its agent, your API deployment, and a pipeline worker are different roles. Your organization’s launcher or integration may create pods; a JIL definition alone does not tell us which component creates them. If the current pod is just a launcher, create the execution worker separately.

02 / Before and after

The fragile part is one long request

A synchronous request can work in a controlled environment. Its completion depends on a chain of client, proxy, route and server timeouts, plus connection and process survival. An async web framework may handle waiting efficiently, but it still leaves the result tied to that request.

ConcernOne long requestSubmit and monitor
Connection drops at minute 25The caller may not know whether work stopped, continued or finished.The caller queries the same durable run.
Submission response is lostA blind retry can start duplicate work.The same idempotency key returns the same run.
API pod restartsIn-process execution may be interrupted.The worker and run record survive independently, subject to their own infrastructure.
Final successUsually the final response, if it arrives.The run’s committed terminal state, translated to the wrapper exit code.
Resource useLong-lived request state; blocked threads depend on framework.Short requests; a lightweight monitoring process still exists.

OpenShift supports route timeout configuration. Increasing it may be a temporary mitigation, but every other timeout layer still needs review. Use your deployed OpenShift version’s documentation and actual ingress settings. [3]

03 / Reference architecture

Separate orchestration, tracking and execution

A 30-minute example

00:00
Submit DAILY_BALANCE_LOAD

AutoSys starts the wrapper. It posts the pipeline name, business date and stable invocation ID.

00:02*
Accept durably

The API commits run r-001 and dispatch intent, then returns 202 Accepted. The wrapper remains running.

00:10*
Start the worker

The dispatcher creates Job pipeline-r-001. The worker records RUNNING and processes the pipeline.

00:30
…
Monitor with short calls

Approximately every 30 seconds, GET /runs/r-001 reports the latest durable state. Temporary network failures trigger bounded retries.

30:00*
Publish and finalize

Output is committed, completion checks pass, and SUCCEEDED is stored. The wrapper observes it and exits 0; AutoSys can release dependent jobs.

*Illustrative timings. Polling adds up to roughly one polling interval to discovery under normal conditions. Worker startup, queueing and outages may add delay.

    05 / Proposed API contract

    Two essential endpoints

    This contract is a design choice for your service. HTTP 202 indicates acceptance, not completion; HTTP itself does not later deliver another final status for the original request. [1]

    1. Submit a logical run

    POST /runs
Authorization: Bearer <service-credential>
Idempotency-Key: <stable-key-for-this-invocation>
Content-Type: application/json

{
  "pipeline_name": "DAILY_BALANCE_LOAD",
  "logical_date": "2026-10-06",
  "invocation_id": "scheduled-2026-10-06-v1"
}

HTTP/1.1 202 Accepted
Location: /runs/r-001
Cache-Control: no-store

{
  "schema_version": 1,
  "run_id": "r-001",
  "state": "QUEUED",
  "status_url": "/runs/r-001"
}

    Commit the run and dispatch intent before returning 202. For the same key and same canonical payload, return the existing run (for example 200) without launching another. For the same key with a different payload, return 409 Conflict. Invalid metadata or unauthorized callers receive an appropriate error, not acceptance.

    2. Inspect that run

    GET /runs/r-001

HTTP/1.1 200 OK
Cache-Control: no-store

{
  "schema_version": 1,
  "run_id": "r-001",
  "pipeline_name": "DAILY_BALANCE_LOAD",
  "state": "RUNNING",
  "phase": "TRANSFORM",
  "attempt": 1,
  "heartbeat_at": "2026-10-06T04:35:00Z",
  "result": null,
  "error": null
}

    A successful status lookup returns 200 even when the pipeline is running or failed. The wrapper must inspect state. On success, result can include output identifiers and reconciliation counts. On failure, return a stable error code and a safe message; retain detailed logs in your observability system.

    A small state machine

    QUEUED→RUNNING→SUCCEEDED
    FAILEDTIMED_OUTCANCELLED

    The lower row contains alternative terminal outcomes. QUEUED can fail during dispatch; RUNNING can fail during execution. TIMED_OUT is an execution deadline verified by the backend, not the wrapper’s monitoring deadline. Within one run, worker retries are attempt changes, not new logical runs. Make terminal results immutable; a deliberate rerun gets a new invocation ID.

    Observed conditionWrapper actionExit code in this example
    QUEUED or RUNNINGContinue checking the same run.No exit
    SUCCEEDEDLog result; release success.0
    FAILED / TIMED_OUT / CANCELLEDLog known terminal outcome.2
    Monitoring budget exhaustedReport outcome unknown; retain run identity.3
    Auth, conflict or contract errorStop and report the integration issue.4

    These nonzero codes are proposed conventions. Configure AutoSys to recognize only 0 as success; explicit success_codes settings govern which codes it accepts. [4]

    06 / Reliability mechanics

    The run ID is useful only if it is durable

    Atomic acceptance and dispatch intent

    Writing a run row and then publishing a queue message separately creates a gap: the API could crash between them. A transactional outbox closes that local gap. Store both records in one database transaction; a dispatcher reads the outbox and launches work later. This is the recommended implementation pattern here, not a guarantee provided by 202.

    submission transaction:
  authenticate and authorize pipeline access
  validate canonical request
  reserve UNIQUE(principal_scope, idempotency_key)
  if an existing key is found:
      compare request_hash; return existing run or 409
  insert run(state=QUEUED, request_hash, pipeline_version, ...)
  insert outbox(run_id, event="START_RUN")
  commit
return 202 with the committed run_id

dispatcher:
  claim outbox item using a lease / row lock
  ensure Job named from run_id exists (create-or-read)
  verify existing Job belongs to this run
  persist Job UID; mark intent delivered
  reconcile after crashes; do not generate a fresh Job name

    If Job creation succeeds but the dispatcher crashes before saving the result, it discovers the same Job on retry. Retain Job identity and durable dispatch state so cleanup cannot cause an old intent to start another execution.

    Idempotency has two layers

    Submission idempotency

    One intended invocation maps to one run. Use a stable business date plus invocation ID; scope the key to the caller or tenant. Automatic retries keep the same key. An approved new execution uses a new ID.

    Output idempotency

    A restarted worker must not duplicate data or external effects. Use run-scoped staging, transactional publication or a manifest, and unique business keys. Choose one writer per output partition when runs can overlap.

    Kubernetes Jobs can start the same program more than once, even with one completion and parallelism one. A Job therefore does not provide exactly-once business execution. [2] Use compare-and-set attempt ownership and fencing tokens where concurrent attempts could publish. A lease alone does not stop an old worker from writing after its lease expires.

    Make “success” an application result

    A pod being Running means the container is active. A process exiting successfully is useful evidence only if the worker defines success correctly. Verify required steps, data checks and final output publication before persisting SUCCEEDED. If output commits but the status update fails, a retry or reconciler checks the run’s durable output manifest and repairs status without republishing.

    FailureExpected recoveryRequired mechanism
    Reply lost after acceptanceRetry submit; retrieve the original run.Unique idempotency key and payload hash.
    API pod restartsPoll another API instance; execution continues independently.Shared database; external worker.
    API crash before transaction commitRetry creates the run once.Database transaction rollback.
    Dispatcher crash after Job creationFind the existing Job and repair bookkeeping.Deterministic name, UID checks, reconciliation.
    Worker dies mid-loadRetry a safe attempt or fail durably.Idempotent output, checkpoints, bounded retries.
    Heartbeat becomes staleInvestigate and reconcile before finalizing.Heartbeat plus worker/Job evidence; avoid false failure from a temporary outage.
    Wrapper pod disappearsRestart monitor; recover the same run via the same key.Invocation ID outside ephemeral pod storage.
    Database is unavailableDo not accept untracked work; retry within budget.Fail closed for acceptance, restore tracking availability.
    07 / Implementation examples

    Keep your processing logic; move its owner

    Extract the long operation into a callable such as execute_pipeline(run_id). The API owns acceptance. The worker owns execution. The reconciler owns recovery of tracking gaps. Do not depend on an API pod’s in-memory thread, background task, or local filesystem for run durability.

    Python AutoSys wrapper — illustrative reference

    Uses Python 3.12 and requests. Adapt authentication, certificate trust and logging to your platform. The total monitoring budget is approximate: a request already in progress may finish after it. This example has not been exercised against your service.

    import hashlib
import json
import os
import random
import sys
import time
from pathlib import Path
from urllib.parse import quote, urlsplit

import requests

# Platform supplies these values; do not put tokens in JIL or CLI args.
BASE = os.environ["PIPELINE_API_BASE"].rstrip("/")
TOKEN_FILE = Path(os.environ["PIPELINE_TOKEN_FILE"])
pipeline, logical_date, invocation_id = sys.argv[1:4]
body = dict(pipeline_name=pipeline, logical_date=logical_date,
            invocation_id=invocation_id)
canonical = json.dumps(body, sort_keys=True, separators=(",", ":"))
key = hashlib.sha256(canonical.encode()).hexdigest()
deadline = time.monotonic() + 7200  # example: 2-hour monitor budget
transient = {408, 429, 500, 502, 503, 504}
terminal_failure = {"FAILED", "TIMED_OUT", "CANCELLED"}
session = requests.Session()

def finish(code, message):
    print(message, flush=True)
    raise SystemExit(code)

def pause(seconds):
    remaining = deadline - time.monotonic()
    if remaining > 0:
        time.sleep(min(seconds, remaining))

def call(method, path, payload=None):
    delay = 2.0
    while time.monotonic() < deadline:
        try:
            token = TOKEN_FILE.read_text().strip()
            response = session.request(
                method, BASE + path, json=payload,
                headers={"Authorization": "Bearer " + token,
                         "Idempotency-Key": key},
                timeout=(5, 10), allow_redirects=False)
        except (requests.ConnectionError, requests.Timeout):
            # Outcome may be unknown. POST retries retain the same key.
            response = None
        except (OSError, requests.RequestException):
            finish(4, "Credential or HTTP client configuration error")

        if response is not None and response.status_code not in transient:
            return response

        # Example supports delta-seconds Retry-After; add HTTP-date
        # support if your API uses that form. Never exceed the budget.
        wait = delay
        if response is not None:
            value = response.headers.get("Retry-After", "")
            if value.isdigit():
                wait = max(wait, float(value))
        pause(wait + random.uniform(0, 1))
        delay = min(delay * 2, 30)
    finish(3, f"Outcome unknown; invocation_id={invocation_id}; resume same key")

def decode(response, allowed_codes):
    if response.status_code not in allowed_codes:
        finish(4, f"API contract/auth error: HTTP {response.status_code}")
    try:
        data = response.json()
    except ValueError:
        finish(4, "API returned invalid JSON")
    if not isinstance(data, dict) or data.get("schema_version") != 1:
        finish(4, "Unexpected API schema")
    return data

if urlsplit(BASE).scheme != "https":
    finish(4, "HTTPS is required")

# Re-running this command with identical arguments recovers the run.
accepted = decode(call("POST", "/runs", body), {200, 202})
run_id = accepted.get("run_id")
if not isinstance(run_id, str) or not run_id or len(run_id) > 128:
    finish(4, "Missing or invalid run_id")
print(f"run_id={run_id}; invocation_id={invocation_id}", flush=True)

while time.monotonic() < deadline:
    status = decode(call("GET", "/runs/" + quote(run_id, safe="")), {200})
    if status.get("run_id") != run_id:
        finish(4, "Status response run_id mismatch")
    state = status.get("state")
    print(f"run_id={run_id}; state={state}", flush=True)
    if state == "SUCCEEDED":
        finish(0, f"Pipeline succeeded: {run_id}")
    if state in terminal_failure:
        finish(2, f"Pipeline terminal failure: {run_id}; state={state}")
    if state not in {"QUEUED", "RUNNING"}:
        finish(4, "Unknown state; refusing to report success")
    pause(30 + random.uniform(0, 3))

finish(3, f"Monitoring deadline; outcome unknown for {run_id}")

    Production additions: validate arguments, emit structured logs and metrics, support your credential renewal flow, handle termination signals, and persist invocation identity in the scheduler’s durable context. The server must implement the idempotency contract before POST retries are safe.

    Kubernetes Job — one execution pod per run 
    apiVersion: batch/v1
kind: Job
metadata:
  name: pipeline-r-001  # derive from durable run ID
  labels:
    app: pipeline-worker
    run-id: r-001
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 0       # start here until worker retries are safe
  activeDeadlineSeconds: 5400  # example execution budget: 90 min
  ttlSecondsAfterFinished: 86400
  template:
    metadata:
      labels:
        app: pipeline-worker
        run-id: r-001
    spec:
      serviceAccountName: pipeline-worker
      restartPolicy: Never
      securityContext:
        runAsNonRoot: true
      containers:
      - name: worker
        image: registry.example.internal/pipeline-worker:release-tag
        command: ["python", "-m", "pipeline_worker"]
        args: ["--run-id", "r-001"]
        resources:
          requests:
            cpu: "250m"
            memory: "512Mi"
          limits:
            cpu: "2"
            memory: "2Gi"
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
          seccompProfile:
            type: RuntimeDefault

    The image must support the OpenShift-assigned user identity. Supply database and source credentials through approved secret mechanisms. Create the referenced service account and appropriate access policies. Resource values are placeholders to size from measurements.

    activeDeadlineSeconds bounds the Job’s execution lifetime; backoffLimit bounds retries. A Job deadline failure is separate from a client-side monitoring timeout. [2] Raise retry limits only after output idempotency and error handling are implemented. Keep run history after Job cleanup, and reconcile terminal status before deleting evidence.

    08 / Operating the design

    Use separate budgets for separate responsibilities

    Budget / controlIllustrative starting valuePurpose
    HTTP connect / read timeout5 s / 10 sBound each network attempt; these are not an end-to-end request deadline.
    Submission targetNormally a few secondsValidate and persist; do not run ETL inside submission.
    Polling cadence30 s + small jitterBalance completion visibility and request volume.
    Queue-age policy10 min, then reconcile and alertDetect dispatch or capacity problems before workers start.
    Worker Job deadline90 minBound execution separately from observation.
    Wrapper monitor budget2 hAllow queueing, execution and result recovery.
    Scheduler / launcher runtime capAbove the wrapper budget + cleanup marginAvoid killing monitoring before it can report its own result.

    Set these from your pipeline SLA, observed duration and failure recovery policy. Align proxy and route timeouts with the short API calls. Do not copy example values as production defaults.

    30-minute run ÷ 30-second interval ≈ 60 status checks
    100 active runs ÷ 30-second interval ≈ 3.3 GET requests/second

    Nominal estimates exclude the first/final checks, jitter and retries. Each waiting wrapper uses little active CPU while sleeping, but still reserves its process or pod resources.

    Data worth retaining

    Store the run ID, principal scope, idempotency key, canonical request hash, pipeline version or metadata snapshot reference, business date, state version, phase, attempt, timestamps, heartbeat, Job name and UID, final output manifest, and safe error code. Record input snapshot references where reproducibility matters.

    Useful operational signals

    • Queue age and dispatch latency: distinguish “accepted” from “started.”
    • Execution and phase duration: identify slow transformations or destination commits.
    • Stale heartbeats and status lag: trigger investigation and reconciliation, not immediate success or failure.
    • Deduplication hits and attempt count: identify retries while keeping logical run counts accurate.
    • Unknown outcomes: track monitor failures separately from known pipeline failures.

    Correlate logs using the run ID across AutoSys, API, dispatcher and worker. Protect submit, status and cancel endpoints with service authentication and pipeline-level authorization. Scope worker permissions to its task; do not grant broad cluster access just to poll run status.

    09 / Choosing an approach

    Polling is the practical first step

    ApproachBest fitTradeoff
    Submit + poll + exitYour current AutoSys command-job model.Simple completion mapping; monitor process or pod stays alive.
    Submit job + separate monitor jobYou want acceptance and completion visible separately.Persist run identity between jobs; downstream jobs depend on monitor success.
    Callback / event completionYou need to release waiting pods, and your scheduler has a supported completion integration.Implement authenticated delivery, duplicate handling, event ordering and reconciliation; capability depends on your installed integration.
    AutoSys launches a worker Job directlyThe launcher already supports Kubernetes Jobs and terminal result tracking.Can simplify the path; still needs durable identity, output safety and business-result semantics.
    Extend synchronous timeoutsShort-term mitigation for bounded, controlled workloads.Does not resolve lost-response ambiguity or duplicate side effects.

    Suggested rollout: implement durable submit/status endpoints and the wrapper first; use an existing durable worker system if available. Add a Job dispatcher if per-run execution pods suit your workloads. Consider scheduler-native event completion when waiting pod cost or scale justifies the additional integration.

    10 / Evidence before adoption

    Prove the behavior with controlled failures

    This architecture can make the process recoverable and observable when its durable handoff, execution and output rules are implemented. No HTML example can guarantee performance or correctness in your cluster. Validate these scenarios with the actual API, launcher, database and worker.

    ExercisePassing observation
    Run a 30–60 minute pipelineSubmission returns promptly; AutoSys stays running; downstream jobs wait for verified success.
    Drop the submit response after commitRetry returns the same run ID; no additional logical run or duplicate publication.
    Submit the same key concurrentlyOne run row and one durable intent; mismatched payload gives 409.
    Restart API and dispatcher pods at handoff boundariesThe run remains discoverable; dispatch resumes or attaches to the existing Job.
    Kill the worker during write and after output commitPartial output stays unpublished; committed output is recovered without duplication.
    Fail a transformation or data validationA terminal failure is recorded and the wrapper exits nonzero; downstream jobs do not start.
    Interrupt status calls or exhaust monitor timeNo false success; outcome unknown is distinguishable; resuming keeps the same run identity.
    Exercise execution deadline and Job cleanupReconciled terminal state survives pod/Job deletion; old dispatch intents cannot relaunch work.
    The invariant to protectOne intended invocation has one durable run identity. Execution can have multiple attempts. Published business effects remain controlled and deduplicated. AutoSys success is emitted only after the durable business result is successful.
