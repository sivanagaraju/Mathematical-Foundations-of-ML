01 · The problem

Acceptance is different from completion.

AutoSys must start the intended pipeline. AutoSys must release the next pipeline only after the required output succeeds.

What we know

  • The API uses a pipeline name to find processing details.
  • A run can take 10–60 minutes.
  • AutoSys coordinates dependent pipelines and groups.

What we must confirm

  • Does the API need to remain?
  • Who starts and tracks the worker?
  • How many runs execute at the same time?
  • Which scheduler completion interfaces are available?

Your J1/J2 sketch is one candidate. The report compares other candidates before it recommends a choice.

Use this success rule.

The worker verifies the output. The observer verifies the exact run result. AutoSys then evaluates the dependent job conditions.

The report uses ASD-STE100 writing principles. Sentences are short. Terms keep one meaning. Descriptions name the component that performs each action.

02 · Time and resource use

A short API request can start a long worker run.

The API can return acceptance near the start. The worker can continue for 30 minutes. A monitor or bridge still owns completion checks.

One synchronous request

The client and API keep the request active. A connection failure can hide the final business result.

One asynchronous run

The API stores the run and returns its ID. An independent worker executes the code. A separate observer reads the result.

HTTP 202 confirms acceptance. It does not confirm processing completion. [1]

Keep resource use visible.

A sleeping monitor uses little active CPU. Its pod can still reserve CPU and memory.

03 · Responsibilities

Different components control different parts.

ComponentActionEvidence
AutoSysStarts commands and evaluates outer dependencies.Job status and required box conditions.
Client jobSubmits work or reads its result.Stable invocation key and exact run ID.
Run serviceStores accepted runs and exposes status.Shared run record and input version.
DispatcherStarts work from stored dispatch instructions.Job identity or task identity.
WorkerCalls the pipeline code and commits output.Output checks and publication evidence.
Monitor or bridgeVerifies and reports the exact result.Observation state or completion delivery record.

The dispatcher can be an existing platform service. The diagrams place the dispatcher within the run service lane for options C–F.

OpenShift starts the worker container after the dispatcher creates its Job. The container entry point calls the worker code.

The first lane in E, F, and G combines AutoSys with its submission client. The client sends the API request.

Separate these architecture choices.

QuestionChoices
How does work start?Direct command, short API request, queue consumer, or workflow start.
Who executes the code?Command process, container worker, queue worker, or workflow task.
Who observes completion?Client, J2, shared coordinator, event bridge, or workflow observer.
Who completes the AutoSys gate?Command exit, supported adapter, or explicit verifier job.

A queue moves work to workers. Polling reads a result. You can use both in one design.

    06 · Reliable handoffs

    Protect the request, the output, and the scheduler cycle.

    Store acceptance before the reply.

    The run service stores the run, its invocation mapping, and dispatch intent in one transaction.

    A dispatcher reads the intent after commit. It creates or finds the worker execution. It records the execution identity.

    The outbox pattern protects this local record-to-message handoff. Receivers must still handle duplicates. [9]

    Store output evidence before success.

    The worker verifies the output commit. If status fails after commit, recovery reads the output evidence before it repeats work.

    The destination must support the required commit guard. A separate run database cannot make the destination write atomic.

    Bind completion to the intended cycle.

    A reused AutoSys job name can refer to a later cycle. A bridge must check the run ID and binding generation.

    The bridge stores received events before acknowledgement. A recovery processor handles stored events that have not completed.

    Broker confirmation and consumer acknowledgement are different from business completion. [10]

    07 · Code entry points

    The worker starts the actual processing code.

    The following example uses option C. The same worker contract can support C, D, E, F, or G.

    1. AutoSys starts the client.

    run-and-monitor P1 --invocation batch-001/P1

    The client sends the request with the same key on every submission retry.

    2. The API stores the intended run.

    submit(request, key):
    authorize(request.pipeline)
    with database_transaction():
        run = find_exact_run(key)
        if run exists:
            require_same_request_hash(run, request)
            return run.id
        run = insert_unique_run(key, pinned_input)
        insert_dispatch_intent(run.id)
    return Accepted(run.id)

    A unique constraint protects concurrent submissions. A different request under the same key returns a conflict.

    3. The dispatcher starts execution.

    dispatch(intent):
    claim_with_bounded_lease(intent)
    job = create_or_find_job(intent.run_id)
    store_job_binding(intent.run_id, job.uid)
    mark_intent_delivered(intent)

container entry point:
    python -m pipeline_worker --run-id r-001

    A recovery check finds the Job after an uncertain creation response. The check must not create a second logical execution.

    4. The worker processes the data.

    worker_main(run_id):
    run = load_run_and_pinned_input(run_id)
    if verified_publication_exists(run_id):
        reconcile_success(run_id)
        return
    ownership = claim_attempt_with_fencing(run_id)
    source = read_source(run.input_snapshot)
    staged = transform_and_stage(source)
    verify_required_checks(staged)
    require_current_ownership(ownership)
    commit_with_destination_guard(staged, ownership)
    persist_or_find_publication_evidence(run_id)
    record_success_or_reconcile_commit_gap(run_id)

    The destination must enforce the ownership guard. A lease alone cannot stop an old worker from writing.

    5. The client reports the final result.

    monitor(key):
    run_id = resolve_exact_run(key)
    repeat within monitor_budget:
        result = read_status(run_id)
        if result.state == SUCCEEDED:
            validate_result_identity(result, key)
            exit(0)
        if result.state is terminal_failure:
            exit(nonzero)
        wait_with_jitter()
    report_observation_unknown()
    exit(nonzero)

    A monitor timeout blocks downstream work. It does not rewrite the business run as failed.

    If the worker starts remote Spark work, store the application ID. Observe that application until the required business result completes.

    The code is design pseudocode. Database races, cancellation, credentials, and destination guards need implementation for the actual platform.

    08 · Failure and recovery

    A failed observer and a failed pipeline are different.

    Business result

    This record states what happened to the output. Examples are QUEUED, RUNNING, SUCCEEDED, FAILED, and confirmed CANCELLED.

    Observation result

    This record states whether the observer knows the result. A stopped monitor can lose the result while the worker continues.

    Try the three failure scenarios.

    Select C or D in the walkthrough. Choose a lost reply, a stopped monitor, or a commit-to-status failure.

    The red mark shows the failure. The purple arrow shows recovery. The gate remains blocked until result verification.

    Cancellation needs a complete protocol.

    1. Store the cancellation request.
    2. Signal the actual execution owner.
    3. Check whether output publication already completed.
    4. Confirm the stopped execution or the completed result.
    5. Report the final outcome to the intended scheduler cycle.

    Check recovery before rollout.

    • Drop the submit reply after acceptance.
    • Stop the API after it stores a run.
    • Stop a worker after output commit.
    • Stop the monitor while the worker continues.
    • Send a repeated or old completion event.
    • Run two invocations against the same output partition.
    • Recover the required parent boxes after J1 or J2 failure.

    Success requires correct output and correct attribution. Recovery must not release a different invocation.

    11 · Terms

    Use one term for one meaning.

    TermMeaning
    InvocationOne intended pipeline run for one batch and input version.
    Invocation keyA stable name for the intended run. A retry uses the same key.
    Run IDThe service identifier for the stored run record.
    DispatcherA service that starts accepted work from a stored dispatch instruction.
    WorkerA program that executes the pipeline code.
    MonitorA program that reads the exact run result.
    PollingRepeated status requests at a defined interval.
    CommitThe destination action that makes the output permanent under its storage rules.
    Publication manifestStored evidence that identifies the committed output and its run.
    OutboxStored instructions for messages that a delivery process must send.
    InboxStored received messages that a processor must check and apply.
    Scheduler bindingA stored link between one run and one scheduler cycle.
    Binding generationA version that distinguishes the current binding from an older binding.
    Fencing tokenAn ownership version that the destination checks before it accepts a write.
    ReconciliationA recovery check that compares records and repairs a known difference.
    IdempotencyA repeat action produces the same intended effect. It does not add another effect.
